Replace in-memory Maps with transactional `bun:sqlite` repositories, versioned migrations, and exact mid-match state recovery for the authoritative backend.

## Specs

Source: GitHub issue #8 "[P1][Persistencia] Implementar SQLite real con transacciones y recuperación del estado". Requirement strings are quoted verbatim (Spanish preserved).

- **S1** — Issue #8 problem: "`SqliteLocalSettlementProvider.ts` utiliza `Map` en memoria; `schema.sql` documenta la estructura, pero no hay persistencia conectada. Un reinicio pierde inventario, escrows, comandos y estado de las partidas." Check: no functional state required by the acceptance criteria lives only in `Map`s; the settlement path and match state survive a process restart.
- **S2** — Issue #8 scope: "Implementar repositorios SQLite transaccionales para compañías, inventarios, contratos, lotes, escrows y grants." Check: each named entity has a transactional repository over SQLite, exercised by tests through public repository/match APIs.
- **S3** — Issue #8 scope: "Persistir cola de comandos e idempotencia; usar migraciones versionadas." Check: the command queue, processed idempotency keys and acknowledgement ledger round-trip through SQLite; a versioned migration runner applies schema versions in order on boot.
- **S4** — Issue #8 scope: "Garantizar unicidad de reservas y consistencia entre saldos y movimientos." Check: UNIQUE/transaction constraints reject duplicate reservations and conflicting movements; balance and movement rows stay consistent within one transaction (rollback leaves no partial rows).
- **S5** — Issue #8 scope: "Reiniciar el backend a mitad de una partida y reconstruir el estado exactamente." Check: an integration test drives a match to a mid-game tick, closes the process/server, reopens the same database, and byte-compares the full reconstructed state (snapshot-based, per A4) against the pre-close state.
- **S6** — Issue #8 acceptance: "Reinicio de proceso no pierde operaciones confirmadas." Check: acknowledged requests and executed command statuses from before the restart are visible with identical results after it, including at the 1024-ack capacity boundary semantics pinned by `backend/test/limits.test.ts`.
- **S7** — Issue #8 acceptance: "Reservas, pagos y entregas son transacciones ACID." Check: tests commit multi-row operations atomically and prove rollback on induced failure leaves every table unchanged.
- **S8** — Issue #8 acceptance: "Reintentos no duplican movimientos." Check: replaying identical request/command idempotency keys against the reopened database never creates a second movement, in both idempotency stores (match-scoped command keys and the HTTP ack ledger).
- **S9** — Issue #8 acceptance: "Test de recuperación compara hashes/estado completo antes y después." Check: the recovery test computes a full-state comparison before/after (A4) and fails on any divergence; the partial `calculateStateHash()` is not used as the sole oracle.
- **S10** — Issue #8 acceptance: "El nombre `SqliteLocalSettlementProvider` describe una implementación SQLite auténtica." Check: that provider performs its lots/escrows/reservations math against SQLite tables, with tests; no `Map`-only storage remains behind the name.
- **S11** — Issue #8 dependency and references: "Dependencia: #6. Referencias: `src/persistence/SqliteLocalSettlementProvider.ts`, `src/persistence/schema.sql`." Check: #6 (authoritative backend) is closed and its backend suite stays green; those two files are reworked or superseded, and `schema.sql` evolves through versioned migrations.

### Bounded assumptions

- **A1**: Driver is `bun:sqlite` (built into Bun 1.4.2): every runtime path is Bun (`bun test`, `bun backend/main.ts`, Docker `oven/bun:1.4.2`), so no new dependency is added. `tsx` is unused.
- **A2**: Branch `feature/sqlite-persistence` stacks on the QA branch tip `feature/qa-test-suite` (`ec14a4b`) — corrected from the initial "off 8475520" plan when the branch was actually created (L6): stacking keeps the CI workflow and the 265-test suite as the differential baseline (stronger for A3) and matches the chained-PR delivery pattern; the SQLite PR will use `feature/qa-test-suite` as base so it shows only its own commits. The QA work is not reworked here.
- **A3**: Restore support is new ADDITIVE API (read/restore surfaces on `CommandQueue`, `FactoryMatch`, engine hydration from repository rows). Tick/production logic is not changed; the existing backend + engine suites stay green as the differential baseline.
- **A4**: Exactness oracle = deep snapshot compare via `createSnapshot()`-grade data (includes lines, activeBatch, contracts), because `calculateStateHash()` is partial (QA finding L12). A dedicated recovery-comparison helper is written for the test only.
- **A5**: `McpGateway` is not instantiated by `backend/src` today; grants/audit persistence is implemented and tested at the repository layer (tables already named in `schema.sql`) WITHOUT wiring the MCP gateway into the backend — that is issue #9.
- **A6**: Both idempotency stores persist (engine match-scoped processed keys and the match ack ledger `http:${matchId}:${requestId}`); the ack cursor and execution history restore together so statuses never regress to `queued`.
- **A7**: Docker: add the persistence sources to the image COPY, run the DB under a writable path for the non-root `bun` user, and document/add a compose volume for restart survival; `restart: "no"` stays as-is (process-restart acceptance, not auto-restart policy).
- **A8**: New tables extend `schema.sql` (which lacks command queue, idempotency, ack ledger, tick/match metadata, line `activeBatch`, and history): migrations own the delta from day one; the file documents version 1.
